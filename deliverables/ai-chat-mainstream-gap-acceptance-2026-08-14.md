# 灵枢 AI 对话主流产品差距与验收清单

> 日期：2026-08-14
> 背景：此前多次按“主流产品 / GitHub 项目”修复 AI 对话区，但用户仍连续遇到 PPT 生成、Skill 自动调用、产物按钮、引用来源、进度反馈、建议选项等问题。本文把对标结论转成可验收清单，避免继续做零散补丁。

## 1. 结论

灵枢 AI 对话区已经补了很多局部能力，但还没有达到主流产品的“任务闭环”体验。

主流产品不是只把模型回答显示出来，而是把一次用户请求拆成清晰的产品状态：

1. 识别用户意图。
2. 自动选择工具 / Skill / 文件上下文。
3. 展示正在做什么。
4. 生成可交付产物。
5. 给出产物操作按钮。
6. 给出下一步选项。
7. 出错或半截输出时自动恢复。
8. 保留可追溯运行记录。

灵枢目前最大的问题是：第 2、3、4、5、7 步都有补丁，但还没有形成统一的状态机和验收规则。

## 2. 对标对象与关键启发

| 对标对象 | 主流做法 | 对灵枢的启发 |
|---|---|---|
| Open WebUI | 明确区分 Native Features、Workspace Tools、MCP、OpenAPI；工具权限和安全风险在 UI/文档中明确说明。 | 灵枢 Skill 需要区分“自动选择、手动选择、实际执行、仅加载说明”，并在聊天里可见。 |
| Open WebUI RAG | 区分 File Context 和 Knowledge/RAG，并提供 citations。 | 灵枢不应默认混入历史知识库；本轮附件、项目资料、知识库、归档记忆要分层显示。 |
| LibreChat Agents | Agent Builder 中显式选择工具；Skills 可手动、自动发现或始终应用；Artifacts 用独立 UI 展示。 | 灵枢的 PPT、文档、图表等应进入 Artifact 卡片，而不是只作为普通 Markdown。 |
| LibreChat Tools | 工具通常绑定到 Agent，并且需要配置、测试、在聊天中实际使用。 | 灵枢自动 Skill 触发后，必须让用户看到“已自动使用 marp-slide / pptx”。 |
| Dify | Workflow/Tool Run 有 inputs、outputs、status、error、elapsed_time、steps。 | 灵枢需要把生成过程变成可追踪步骤，而不是一个模糊进度条。 |
| AnythingLLM | Workspace、文档、RAG、Agent、MCP、citations 是一体化工作流。 | 灵枢要利用桌面本地优势，但必须保证引用、产物、工具执行闭环。 |

## 3. 当前灵枢 AI 对话的真实问题

### P0. 产物任务没有统一闭环

现象：

- 用户说“生成 PPT”，AI 可能生成 Markdown，但卡片之前仍显示“生成 DOCX”。
- 已新增 PPTX 导出后，仍缺少导出质量验收，例如 PowerPoint/WPS 打开是否正常、主题是否像 PPT。
- 产物类型识别靠正则，容易把普通文本误判为幻灯片，或漏掉真实产物。

主流做法：

- Artifact 是一等对象，有类型、标题、预览、导出、版本、重新生成。

灵枢目标：

- 每条产物回复必须生成 `artifact` 元数据，而不是靠正文正则猜。

验收：

- 输入“我想编写一个关于 AI 安全的 PPT”。
- 回复必须出现“幻灯片产物”卡片。
- 卡片必须有“预览”和“生成 PPTX”。
- 点击“生成 PPTX”必须得到可打开的 `.pptx` 文件。
- 不能出现“生成 DOCX”作为主要按钮。

### P0. 自动 Skill 调用不可见

现象：

- 后端已自动注入 `marp-slide` 和 `pptx` Skill，但用户看不到“自动调用了哪些 Skill”。
- 聊天里的 tool call 展示更像调试信息，不像主流产品的“正在使用某能力”状态。

主流做法：

- 工具/Skill 是否启用、是否运行、是否成功，应在 UI 上可见。

灵枢目标：

- 当用户请求 PPT 时，输入后立即展示“已自动选择：marp-slide、pptx”。
- AI 回复卡片下方展示 Skill 使用证据：模式、耗时、是否实际执行。

验收：

- 输入 PPT 请求后，生成过程中可见 “正在使用 marp-slide / pptx”。
- 完成后可展开查看 Skill 运行记录。
- 如果没有找到相关 Skill，应显示“未找到 PPT Skill，已使用内置导出器兜底”。

### P0. 生成过程没有真实步骤

现象：

- 现在的进度条是估算百分比，不代表真实步骤。
- 用户看到“停住了”时，不知道是在连接模型、生成正文、导出文件、还是保存归档。

主流做法：

- Dify/Flowise 这类工作流产品会展示节点状态。
- 主流 Chat 产品也会展示“搜索中 / 阅读文件中 / 生成中 / 调用工具中”。

灵枢目标：

- 对话运行态要变成 step list：
  - 识别任务
  - 选择 Skill
  - 读取附件/知识
  - 调用模型
  - 生成产物
  - 导出/保存

验收：

- PPT 请求生成中，至少看到 3 个状态：`识别为幻灯片任务`、`已选择 PPT Skill`、`正在生成幻灯片内容`。
- 如果中断，最后状态应显示错误原因和可点击恢复动作。

### P0. 半截回复和坏输出缺少通用恢复

现象：

- PPT 已加兜底，但只是对 PPT 特例。
- 其他产物任务如文档、表格、图表、流程图仍可能半截停住。

主流做法：

- 产物生成应有 schema / artifact protocol，结果不完整时可以恢复。

灵枢目标：

- 对产物任务做统一完整性校验。
- 如果模型输出不完整，自动补全或显示“继续生成”按钮。

验收：

- 模型只输出半句时，界面不能停在半句。
- 必须出现以下之一：
  - 自动补全后的产物；
  - “继续生成”按钮；
  - 明确错误卡片和恢复建议。

### P1. 建议选项不是结构化数据

现象：

- 目前是从正文里抽取“可选下一步”，容易误识别或漏识别。
- 用户希望像主流产品一样直接点击选项确认。

主流做法：

- follow-up chips 通常来自结构化 suggestion 元数据，而不是解析正文。

灵枢目标：

- 后端返回 `suggestions: [{label, prompt, action}]`。
- 前端优先用结构化 suggestions，正文抽取只作为兜底。

验收：

- AI 需要用户选择时，按钮必须稳定显示。
- 点击后填入输入框或直接发送，并说明当前行为。
- PPT 正文里的项目符号不能被误判为建议选项。

### P1. 引用来源仍不够主流

现象：

- 已修复附件误显示 Obsidian，但引用还是卡片式堆叠。
- 缺少正文编号引用 `[1] [2]`。
- 来源不能直接打开原文件定位片段。

主流做法：

- RAG 引用应可追踪、可打开、可复制、可定位。

灵枢目标：

- 回答正文中显示来源编号。
- 来源卡片支持打开附件、打开 Vault 文件、复制片段。
- 明确区分：本轮附件、当前项目、知识库、历史归档。

验收：

- 上传文档后提问，引用来源不能显示 Obsidian。
- 每个引用有类型、文件名、片段、打开动作。

### P1. 归档和知识库关系还不够清楚

现象：

- 顶部已有“已归档”标签，但用户仍可能误解为“已进入知识库检索”。
- 归档成功后没有明确路径入口。

主流做法：

- 历史归档、记忆、知识库/RAG 是分层概念。

灵枢目标：

- 归档状态提供“打开归档文件”。
- 知识检索开关显示当前是否启用。
- 每轮回答注明是否使用知识库。

验收：

- 普通 PPT 生成不应引用历史知识库。
- 明确说“结合知识库”时才出现知识库来源。

### P2. 产物预览还不像 PPT

现象：

- Marp Markdown 可预览，但不是幻灯片视图。
- PPTX 导出是基础版，缺少主题、版式、封面、目录、图示。

主流做法：

- Artifact 预览应按产物类型渲染。

灵枢目标：

- 幻灯片产物进入 slide preview。
- 支持主题选择、页数选择、重新生成某页。

验收：

- PPT 产物预览不是普通长文，而是分页幻灯片。
- 有“上一页/下一页/导出/重生成本页”。

## 4. 已修复但仍需补齐的地方

| 已修复项 | 为什么仍不够 |
|---|---|
| DSML 清洗 | 只是防脏输出；不能替代结构化工具调用协议。 |
| 文档/幻灯片产物卡片 | 仍靠正文正则识别；需要 artifact 元数据。 |
| PPTX 导出 | 已可生成文件；还缺模板、预览、质量验收。 |
| 自动注入 PPT Skills | 后端已注入；前端还不可见。 |
| 可选下一步按钮 | 目前是正文抽取；需要后端结构化 suggestions。 |
| 生成进度 | 当前是估算状态；需要真实 step 状态。 |
| 归档状态 | 已显示状态；还缺打开路径和知识库开关。 |

## 5. 建议按这个顺序继续修

### 第一批：把常用文本产物真正做闭环

1. 返回结构化 `artifacts`，包含 `type`、`title`、`content`、`exports`。
2. 覆盖常用文本产物：Word / PPT / 表格 / Markdown / HTML。
3. 返回结构化 `steps`，展示自动选择 Skill、模型生成、产物校验、可导出。
4. 前端不再按单一场景特判按钮，而是读取统一的 `artifact.formats`。
5. 产物卡片按类型显示：
   - Word/文档：预览、生成 DOCX、导出 MD、导出 HTML。
   - PPT/幻灯片：预览、生成 PPTX、导出 MD。
   - 表格/Excel：预览、生成 XLSX、生成 CSV、导出 MD。
   - Markdown：预览、导出 MD、导出 HTML、生成 DOCX。
   - HTML：预览、导出 HTML、导出 MD。
6. 自动 Skill 使用状态显示在消息顶部或进度条中。

### 第二批：把建议选项结构化

1. 后端返回 `suggestions`。
2. 前端按钮优先使用 `message.suggestions`。
3. 点击按钮支持两种行为：
   - 填入输入框
   - 直接发送

### 第三批：把引用和知识库状态做清楚

1. 产物任务默认不使用知识库。
2. 附件任务优先使用本轮附件。
3. 知识库任务必须显示检索范围。
4. 引用卡片支持打开来源。

### 第四批：补主流 Artifact 体验

1. 右侧面板按类型渲染：文档 / 幻灯片 / 表格 / 图表。
2. 幻灯片分页预览。
3. 版本历史。
4. 导出历史。

## 6. 固定验收用例

以后每次改 AI 对话区，至少跑下面 9 个用例：

| 编号 | 输入 | 必须看到 |
|---|---|---|
| A1 | 我想编写一个关于 AI 安全的 PPT | 幻灯片产物卡片、生成 PPTX、自动使用 PPT Skill 状态 |
| A2 | 上传 DOCX 后说“优化这个文档” | 文档产物卡片、生成 DOCX、本轮附件来源 |
| A3 | 上传 PDF 后问“总结重点” | 引用来源显示附件名，不显示 Obsidian |
| A4 | 说“结合知识库整理成报告” | 明确知识库检索来源和引用 |
| A5 | 模型输出半截内容 | 自动补全或显示继续生成按钮 |
| A6 | 让 AI 给三个方案 | 显示可点击建议选项 |
| A7 | 切换模型后发送 | 顶部显示已切换模型，回复 model tag 一致 |
| A8 | 长引用/长文件名 | UI 不溢出、不横向撑破 |
| A9 | 分别要求生成 Word、PPT、表格、Markdown、HTML | 五类常用文本产物都出现产物卡、预览和对应导出按钮 |

## 7. 当前落地进度

- 已新增统一前端产物识别层：`src/utils/chatArtifacts.ts`。
- 已把消息气泡产物卡从 DOCX/PPTX 特判改为通用格式列表。
- 已把右侧预览面板改为通用导出按钮。
- 已新增统一后端导出接口：`POST /api/chat/export-artifact`，支持 `docx`、`pptx`、`xlsx`、`csv`、`md`、`html`。
- 已新增结构化元数据第一版：后端 chat 返回 `artifacts / steps / suggestions / recovery`，前端消息气泡优先读取这些字段。
- 已修正失败路径：模型/API 失败时不生成“ready”的产物卡，只显示步骤和恢复建议。
- 已新增实时 `step` SSE 事件：流式回复开始后会先显示任务识别、模型调用等阶段；顶部生成进度优先读取实时 steps。
- 已收紧默认知识库检索：普通聊天、PPT、Word、表格、HTML 生成不再默认混入 Obsidian；只有明确要求知识库/历史/资料检索才使用全局知识。
- 仍需继续推进：让模型原生输出稳定的 `artifact schema`，并把 `sources` 深链、产物版本历史继续结构化。
